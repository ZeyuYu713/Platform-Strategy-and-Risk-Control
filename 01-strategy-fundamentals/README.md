# 01｜Strategy Product Fundamentals：策略产品基础

## 1. 什么是策略？

在平台业务中，策略（Strategy / Policy）是在特定状态、资源和约束下，决定**对什么对象采取何种动作**的一套可执行规则或决策机制。

形式化地，可表示为：

$$
a_t=\pi(x_t,c_t)
$$

其中 x_t 是时点 t 可观察的对象状态及特征，c_t 是上下文与限制，a_t 是采取的动作，π 是决策策略。

例如：
- 广告策略：根据用户体验状态、广告主需求及库存约束，判断是否展示广告以及展示什么广告。
- 内容策略：根据内容质量、用户偏好与生态约束，决定候选内容的排序、流量扶持或限制。
- 风控策略：根据交易风险、证据与处置成本，决定放行、二次验证、人工审核或拦截。

**策略不等于算法**。策略可能由人工规则、机器学习模型、优化器、人工审核和产品约束共同实现。模型输出风险分数不等于最终处置决定。

## 2. 与功能型产品经理的区别

功能产品主要围绕用户任务与交互完成度设计功能；策略产品则更强调**对大量对象重复进行决策的质量**，其结果往往表现为指标分布、风险成本和长期行为变化。

| 维度 | 功能产品 | 策略产品 |
| --- | --- | --- |
| 决策对象 | 用户任务与功能流程 | 用户、内容、流量、交易或账户等集合 |
| 常见交付 | 页面、交互、流程、权限、API | 目标、特征、规则、模型接口、阈值、实验 |
| 核心问题 | 能否顺利完成任务？ | 采取何种动作、对哪些对象、付出什么代价？ |
| 评估 | 使用率、任务完成率、体验 | 业务收益、误判损失、实验效果、护栏 |
| 典型风险 | 交互复杂、需求不成立 | 数据漂移、策略相互影响、反馈回路、错误处置 |

二者可能重叠：成熟策略系统也需要易用的配置和审核后台。

## 3. 一个策略任务的基本结构

设业务希望降低欺诈损失。不能直接说“把风险阈值调低”。必须明确目标、动作与约束：

**优化目标**：降低净欺诈损失或风险加权成本。

**可用动作**：放行、延迟核验、人工审核、限制某项能力、拒绝交易。

**约束条件**：正常用户误杀率、人工审核容量、处理延迟、用户投诉、数据合规。

**观测数据**：历史行为、实时交易信号、模型输出、审核回执，以及有时间滞后的真实损失标签。

策略问题可抽象为：

$$
\min_{\pi}\ \mathbb{E}[L_{\mathrm{risk}}(\pi)+L_{\mathrm{friction}}(\pi)+L_{\mathrm{operation}}(\pi)]
$$

其中每种损失如何计量需要业务定义。该式是概念性优化目标，不是可直接拿去运行的生产算法。

## 4. “策略有效”必须回答四个问题

第一，它是否对目标对象产生了预期变化？

第二，这种变化是否真的由策略造成，而不是季节、用户组成或其他同时上线的功能造成？

第三，是否存在代价，如正常用户流失、广告主预算下降、低频创作者流量被挤压？

第四，策略是否稳定：在新国家、新活动季、新对抗行为出现时是否失效？

## 5. 最常见的术语

- **Rule（规则）**：明确条件与动作，例如特定证据组合触发补充核验。
- **Score（评分）**：风险程度、相关性、质量或商业价值的预测值；不自动对应行动。
- **Policy（决策策略）**：把分数、规则、约束和业务目标转成最终动作。
- **Threshold（阈值）**：在某个分数或统计值上划分不同动作区间。
- **Feature（特征）**：参与判断的数据，如用户行为或内容统计。
- **Feedback Loop（反馈回路）**：策略改变用户/系统行为，而这些行为又反过来影响未来数据。
- **Guardrail（护栏指标）**：不允许为了主目标恶化到不可接受程度的指标。
- **Rollback（回滚）**：在风险超限时恢复至经过验证的策略版本。
