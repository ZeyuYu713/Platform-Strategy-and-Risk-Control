# 04｜Risk Control & Anti-Fraud：互联网风控与反作弊

## 一、先定义“风险”是什么

互联网风控（Risk Control）是识别、评估和处置可能损害用户、商家、广告主、平台或公众利益的事件，并控制总损失的业务与技术体系。

常见场景：

| 场景 | 可能风险 | 需要保护的对象 |
| --- | --- | --- |
| 交易风控 | 支付欺诈、异常退款、订单滥用 | 用户资金、商户和平台交易 |
| 广告风控 | 虚假流量、异常互动、广告主欺诈 | 预算真实性、广告主信任 |
| 账号安全 | 账号盗用、异常登录、批量滥用 | 正常账户与服务稳定性 |
| 内容安全 | 有害、违规、欺骗性内容 | 用户权益、平台生态 |
| 激励反作弊 | 补贴/奖励滥用、虚假任务 | 活动预算、真实参与者 |

不同场景的证据标准和处置权限不同。账号安全、内容治理与交易风控不应通过一个“万能分数”粗暴统一。

## 二、风险策略的基本链路

~~~mermaid
flowchart LR
  A["风险事件与触发"] --> B["合法可用特征"]
  B --> C["模型评分 / 规则证据"]
  C --> D["分层策略决策"]
  D --> E["放行 / 验证 / 审核 / 处置"]
  E --> F["确认结果、申诉和反馈"]
  F --> G["监测、复盘和更新"]
~~~

这是高层防御框架，不提供可用于规避检测的系统阈值或具体特征组合。

**规则（Rule）**适合明确、可解释的违规条件及政策要求；**模型（Model）**擅长从多维信号中估计风险，但存在偏差、漂移和可解释性问题；**人工审核（Human Review）**用于需要上下文、证据判定或申诉复核的情况。三者协同，而非相互替代。

## 三、处置不是非黑即白

假设某笔交易模型评分偏高，未必应立即永久封禁用户。需要综合：
- 潜在损失的金额、严重性和可逆性；
- 证据是否充分、标签是否可靠；
- 用户正常权益与纠错成本；
- 是否可通过二次验证降低不确定性；
- 审核队列容量与实时决策要求；
- 法律、隐私和程序正当性要求。

可选择与风险等级相适应的动作，优先考虑在可能情况下采用**可逆、比例适当、可申诉**的措施。

## 四、Precision 与 Recall 为什么会冲突？

在二分类的简化设定中：
- **Precision**：被判为风险的样本中，真实风险有多少？
- **Recall**：真实风险中，被策略识别出多少？
- **FPR**：真实正常对象中被错误判为风险的比例。
- **FNR**：真实风险对象中被遗漏的比例。

风控不能只追求 Recall=100%，因为把所有对象都判为风险虽然能达到完全召回，却会给正常用户造成不可接受的损失。

更重要的是，**预测为风险不必直接意味着最终拦截**：模型识别、审核和实际处置的混淆矩阵必须分别统计。

## 五、风险率很低时的“基础率陷阱”

欺诈往往是低发生率事件。即便模型 Recall 很高，FPR 只有几个百分点，仍可能产生大量误报。用 Accuracy（总体正确率）评价会严重误导；必须结合业务基率（Prevalence）与误杀成本。

一组可复算案例与阈值比较见 [风控指标专项](risk-metrics-and-thresholds.md)。

## 六、风控产品岗位实际做什么？

**风控策略产品**并不是只负责训练模型。常见工作包括：
1. 明确风险类型与可观测损失、拆解高风险场景；
2. 与分析、算法、工程、运营和法务确定策略能力与证据标准；
3. 设计模型评分、规则引擎、处置流程、配置后台与监控；
4. 建立灰度、回滚、审批和申诉机制；
5. 评估风险减少的同时，正常用户通过率、转化、投诉和审核负荷是否恶化。

也要区分**风险识别（检测）**、**风险决策（处置）**和**风险损失确认（结果）**的时间线：例如拒付或作弊确认可能延迟，导致短期面板表现与长期真实损失不一致。

## 七、策略复盘中经常忽视的问题

- 样本选择：被拦截对象往往缺乏后续真实行为标签。
- 标签延迟：真实欺诈结果可能数日甚至更久才能确认。
- 对抗漂移：风险行为会随着策略更新发生改变。
- 规则冲突：同一对象可能同时命中放行、审核与限制策略。
- 合规与隐私：不能不加限制地收集或使用个人数据。
- 公平性：不同合法业务群体的误判差异需要审查。
- 误杀与申诉：被错误限制的正常用户需要救济渠道。
